# Offline MMO Revival

**已关服网游的原客户端兼容服务端重建 Skill。**

从留下来的客户端出发，让登录、地图、角色和玩法重新运转起来。

`offline-mmo-revival` 是面向 AI 编程与逆向 Agent 的工程化 Skill。它将客户端逆向、资源与脚本分析、协议还原、服务端实现和客户端联调组织为一套可持续推进的工作流程，目标是**独立实现一个兼容现有客户端的新服务端**。

默认面向本地单机自用：保留客户端的画面、资源与操作方式，优先跑通最小可玩闭环，再逐步补齐功能。

> **当前提供的是执行规范，而不是现成的游戏服务端。** 仓库不包含特定游戏的已还原协议、客户端资源或可直接运行的服务端，也不附带任何游戏版本的兼容性验证结果。

## 核心路线

```text
逆向客户端
    ↓
解资源 / 脚本
    ↓
找网络收发与加解密
    ↓
还原 Packet 格式
    ↓
找 Dispatcher / Opcode
    ↓
搭建最小兼容服务端
    ↓
Login → EnterWorld
    ↓
以客户端行为作为协议 Oracle，逐 Opcode 实现
    ↓
重建游戏状态机与数据库
    ↓
形成兼容原客户端的新服务端
```

这不是“分析完整个客户端，再开始写服务端”的瀑布流程。每一轮只围绕当前目标补齐必要的证据、消息和状态处理；状态机与最小持久化从服务端原型阶段就开始建立。

第一条应当完成的路径是：

```text
启动 → 登录 → 选择或创建角色 → 进入地图 → 移动与基础交互
→ 一个最小玩法循环 → 保存退出 → 重启服务端 → 重登后恢复进度
```

## 项目定位

本 Skill 适用于已有客户端、资源或脚本，需要重新建立本地服务端的项目；也适用于已经找到部分网络函数或 Opcode，但尚未打通登录、进入地图或持续交互的工程。

它约束 Agent 不只交付一份路线介绍，而是在具备工具和运行条件时，直接进行分析、实现、实验与回归，并持续保存能够被下一轮工作接手的记录。

**目标是兼容性重建，不是宣称找回官方内部实现。** 协议兼容、客户端可见行为兼容与官方服务端逻辑一致，是三个不同层次。缺少依据的战斗公式、AI、掉落和经济参数，应作为可替换的“重建规则”明确记录。

默认不建设跨服、分布式、商业运营或大规模并发架构，也不以导出全部美术资源、找到全部 Opcode 为开始实现的前提。

## 快速开始

### 1. 准备客户端与工作目录

保留一份只读原始客户端，为实验创建工作副本。向 Agent 提供实际路径，并尽可能提供客户端版本、启动入口、当前报错、已有分析和允许修改的范围。

以下仅为路径示例，请替换为自己的实际目录：

```text
D:/GameRevival/
├── client-original/    # 原始客户端，只读保留
├── client-working/     # 工作副本，用于本地联调
└── workspace/          # 分析、协议、服务端与测试工程
```

原始材料可以只记录路径和 SHA-256，不必为满足目录结构重复复制大型证据。已有服务端工程和分析目录应优先沿用。

### 2. 让 Agent 读取 Skill

使用支持 Skill 的 Agent 时，按该工具自身的加载规则放置 `offline-mmo-revival` 目录，并确认 `SKILL.md` 已被读取。本文不预设某个产品的专用安装路径。

没有 Skill 加载机制时，可以让能访问本地文件的 Agent 直接读取 `SKILL.md`；也可以将文件作为附件提供，或把其中的指令放入任务上下文。

> 加载 Skill 不会自动提供调试器、文件访问、命令执行或客户端运行能力。应按实际环境提供工具；只能做静态分析时，必须明确哪些结果尚未经过真实客户端验证。

### 3. 发送首次启动提示词

```text
使用 offline-mmo-revival Skill。先读取实际 SKILL.md，再开始执行。

Skill 文件：<SKILL.md 的实际路径或已提供的附件>
原始客户端目录：<只读原件路径>
工作客户端目录：<用于联调的工作副本路径>
工程目录：<实际工作目录>

目标：根据现有客户端，独立重建一个本地单机运行的兼容服务端。

先检查客户端版本、启动入口、资源与脚本、已有工程和可用工具，
判断当前阶段，选择最短可验证闭环开始执行。

优先围绕 Login → EnterWorld 推进，不要先分析完整个客户端，
不要预设具体 Opcode、包头、字段含义或加密算法。

默认保留原始客户端，只在工作副本中记录、实施可撤销的实验变更。
服务端默认监听回环地址，不上传客户端、抓包或内存到外部服务。

已有工程优先沿用。具备执行条件时直接分析、编写代码并验证；
无法运行客户端时，继续能够完成的静态分析和离线测试，明确验证边界。

每轮保存证据并更新协议定义、Opcode 表和 PROGRESS.md。
分别报告已确认事实、推测、临时实现与未完成的客户端联调。
```

### 4. 后续继续同一项目

```text
继续使用 offline-mmo-revival Skill。

工程目录：<已有工作目录>

先读取 PROGRESS.md、协议文档、Opcode 表与最近的实验记录，
复核客户端版本及最后一个可重复的成功闭环。

围绕当前阻塞选择一个最有信息增益的实验，不重复已经完成的分析，
不在缺少新证据时机械重试同一假设，也不从头搭建另一套工程。

完成后更新实现、测试、证据索引和 PROGRESS.md，
说明本轮解锁了什么客户端行为，以及下一步的判定条件。
```

## 执行阶段与验收

阶段编号用于管理进度，不要求严格单向执行。可以从脚本、网络函数或 Dispatcher 入手，再沿当前目标的依赖补齐。

| 阶段 | 主要工作 | 阶段验收重点 |
| --- | --- | --- |
| 0 · 运行基线 | 核实启动链、依赖、配置与初始连接行为 | 能重复到达同一状态，或有证据说明运行阻塞 |
| 1 · 客户端结构 | 定位关键模块、调用链、消息构造与读取入口 | 有可追溯的函数候选与下一步验证目标 |
| 2 · 资源与脚本 | 提取当前闭环所需的消息、地图、角色和配置数据 | 来源明确，提取过程可复现 |
| 3 · 网络与变换边界 | 关联线上字节、变换前后缓冲区和业务读写 | 能解释数据处于哪一处理层 |
| 4 · Packet 格式 | 确认分帧、字段、会话变换与状态更新规则 | 当前消息有独立证据和边界测试支持 |
| 5 · Dispatcher / Opcode | 建立消息、处理入口、字段与前置状态映射 | 关键消息可解释、可定位、可复现 |
| 6 · 最小服务端 | 建立传输、编解码、派发与最小会话状态机 | 完成至少一个真实客户端协议交互 |
| 7 · Login | 实现实际存在的协商、认证和角色选择依赖 | 从干净启动稳定进入角色选择或等价阶段 |
| 8 · EnterWorld | 补齐角色、地图、实体与初始化顺序 | 能进入地图并操作，移动与心跳正常 |
| 9 · 逐消息验证 | 通过受控实验实现交互所需的消息与状态变化 | 有定义、证据、实现、正反例和验证范围 |
| 10 · 玩法与存档 | 建立最小玩法循环、权威状态及持久化 | 保存、服务端重启、重登和重复操作可验证 |

## 怎样使用客户端作为协议 Oracle

这里的 **Oracle** 指实验中的观察与验证依据：针对同一客户端版本、同一前置状态，构造有证据支持的候选响应，观察客户端如何解析、迁移状态并发出后续消息。

```text
选择一个可观察目标
→ 固定客户端版本、会话与角色初始状态
→ 提出一个字段、消息或时序假设
→ 构造最小候选响应
→ 只改变一个语义变量及其必需的派生字段
→ 比较解析、状态、业务结果与反例
→ 保存证据，更新规格、实现与回归测试
```

例如，登录成功后仍停留在加载界面，不应直接得出“还缺一个进入世界 Opcode”的结论。应结合客户端接收路径，检查当前初始化依赖是否满足，再验证角色信息、地图资源、对象引用、连接切换或完成标记等候选原因。

**没崩溃、没断线、出现模型，都不能单独作为功能完成的依据。** 需要进一步确认完整读取、正确状态迁移、预期业务变化，以及后续交互和必要的重登结果。

客户端接受某个响应，也不代表响应中的玩法算法或数值与原官方服务端一致。

## 推荐工作区与产出

以下是实际重建项目可按需采用的结构，不要求迁移已有工程：

```text
workspace/
├── PROGRESS.md       # 当前阶段、成功闭环、阻塞与下一项实验
├── evidence/         # 样本清单、哈希、抓包、追踪和截图
├── extracted/        # 提取资源及其来源关系
├── analysis/         # 函数定位、调用关系和实验记录
├── protocol/         # Packet 规格、会话变换、Opcode 表与消息定义
├── server/           # 独立实现的服务端
├── data/             # 静态内容与运行数据，逻辑分离
└── tests/            # 编解码、状态机、回放和客户端回归测试
```

每条 Opcode 记录需要关联版本、连接类型、方向、协议阶段、处理入口、字段、前置状态和证据。**证据状态、实现状态和验证范围应分别维护**，不能因为写出了 Handler，就将推测升级为已确认协议。

| 维度 | 记录方式 | 含义 |
| --- | --- | --- |
| 证据状态 | `unknown` / `inferred` / `verified` | 尚未确定、推测、有明确范围的验证支持 |
| 实现状态 | `todo` / `stub` / `partial` / `complete` | 未实现、临时占位、部分实现、实现完成 |
| 验证范围 | `static` / `codec` / `server` / `client` / `cold-start` | 静态、编解码、服务端、客户端联调、冷启动回归 |

`verified` 必须附带适用条件；`complete` 也不自动代表已完成客户端联调。完整 Opcode 模板与实验记录要求见 [SKILL.md](./SKILL.md)。

每轮工作采用以下报告格式，便于定位进度并继续执行：

```text
当前目标：本轮要解锁什么客户端行为。
已确认：结论、适用版本/状态及证据位置。
本轮变更：新增或修改了哪些文件、消息定义和实现。
验证结果：实际执行的测试，以及通过、失败、未运行的部分。
当前阻塞：缺少的事实、失败层次与尚未排除的假设。
下一步：一个最值得执行的实验及其判定条件。
```

## 完成标准

项目至少需要完成一次可重复的“启动、登录、进地图、基础交互、最小玩法循环、保存、重启服务端、重登恢复”闭环，并交付能够复现该结果的服务端源码、启动说明、数据初始化方式、连接配置、协议记录、测试及已知问题。

最终报告必须分别标注：**原版客户端已验证兼容、仅修改连接配置后兼容、代码修改版才兼容、已实现但未联调、临时 Stub、自行设计的重建玩法，以及尚缺证据的功能。**

成功标准是一个版本明确、行为可验证、存档可持续的新服务端，而不是一张看起来完整的 Opcode 表。

## 常见问题

### 没有官方服务端和历史抓包，还能开始吗？

可以从客户端的消息构造、读取逻辑、脚本注册和状态切换入手，先建立候选消息规格，再用本地服务端逐步验证。没有参考回包时，更需要严格区分推测与验证结果，不能凭空补齐未知协议。

### 必须先解出所有资源、所有脚本和全部 Opcode 吗？

不需要。先提取当前登录或地图闭环的必要内容，沿依赖扩展。某项提取方法是否适用，应由实际客户端及其加载流程验证，而不是预设所有游戏都使用相同资源格式或 Lua 版本。

### 必须使用某一种服务端语言吗？

不必须。已有工程优先沿用；空白项目可以使用 Python 编写协议原型，单机原型可按需要选择 SQLite。是否更换语言或存储方案，应由项目实际需求决定，而不是为了架构完整性推迟首个闭环。

### 能保证原客户端完全不改就能使用吗？

不保证。项目需要如实记录原始版本、连接配置变更和代码变更，分别说明兼容范围。遇到无法取得的原服务端签名或信任材料时，应将其列为明确阻塞；采用本地信任替换的实验版本，不得宣称原版无修改兼容。

### Agent 不能运行游戏时怎么办？

继续完成可执行的静态分析、协议规格、服务端代码和离线测试，并给出针对缺失证据的采集步骤。未运行的客户端联调必须标记为未验证，不能用自行编写的编码器与解码器互测代替原客户端验证。

## 使用范围与提交约定

本项目将工作范围限定为有权分析的客户端，以及本机或明确授权的隔离测试环境。默认只监听回环地址，不操作第三方账号，不使用泄露的服务端源码，不获取或传播第三方密钥，也不擅自上传客户端、抓包或内存到外部服务。

客户端、资源、商标和其他第三方材料的权利不因本 Skill 的使用而改变。请不要在问题反馈、代码提交或发行包中附带无权分发的客户端、资源、源码、凭据和个人数据。本项目不授予任何第三方材料的使用或分发许可。

对流程提出改进或提交兼容性研究记录时，应说明客户端版本、复现步骤、预期与实际结果、证据来源和验证范围；分享前移除敏感信息，并注明必要的脱敏或样本变更。
