# Offline MMO Revival

**已关服网游的原客户端兼容服务端重建 Skill。**

`v1.1.0` · `Go / Python` · `SQLite` · `Lua / Opcode` · `Attach 诊断与测试回填`

从留下来的客户端出发，让登录、地图、角色和玩法重新运转起来。

`offline-mmo-revival` 是面向 AI 编程与逆向 Agent 的工程化 Skill。它将客户端逆向、资源与脚本分析、协议还原、服务端实现和客户端联调组织为一套可持续推进的工作流程，目标是**独立实现一个兼容现有客户端的新服务端**。

默认面向本地单机自用：保留客户端的画面、资源与操作方式，使用 **Go 或 Python + SQLite** 快速建立服务端，先打通登录与进入地图，再通过资源解包、本地 Lua、Opcode 诊断和用户测试逐步补齐功能。

> **当前提供的是执行规范，而不是现成的游戏服务端。** 本仓库的两份文档用于指导 Agent 实现服务端、资源工具、附加采集和自动导出；不包含这些工具的现成实现、特定游戏协议或客户端资源，也不附带任何游戏版本的兼容性验证结果。

## 核心路线

```text
逆向客户端 → 提取登录/进图必需资源 → 定位网络收发与加解密
    ↓
还原 Packet 格式与关键 Dispatcher / Opcode
    ↓
使用 Go 或 Python + SQLite 搭建最小兼容服务端
    ↓
Login → EnterWorld
    ↓
系统解包资源 → 提取本地 Lua → 整理 Opcode 列表
    ↓
[可选：建立资源 / Lua / Opcode 速查网页]
    ↓
服务端日志 + 可用时 Attach 附加诊断 → 用户在游戏中测试
    ↓
自动导出未实现 / 异常 Opcode → 梳理功能、消息与脚本依赖
    ↓
根据本地 Lua / 原生处理器重建逻辑 → 修复 → 客户端复测
    ↓
逐步补齐状态机与 SQLite 存档 → 形成兼容原客户端的新服务端
```

这不是“分析完整个客户端，再开始写服务端”的瀑布流程。**进游戏前只提取必要内容；能进入地图并操作后，主动进行系统资源解包、Lua 提取和 Opcode 梳理。** 状态机与 SQLite 持久化从服务端原型阶段就开始建立，速查网页可选，不阻塞协议修复。

第一条应当完成的路径是：

```text
启动 → 登录 → 选择或创建角色 → 进入地图 → 移动与基础交互
→ 一个最小玩法循环 → 保存退出 → 重启服务端 → 重登后恢复进度
```

## 项目定位

本 Skill 适用于已有客户端、资源或脚本，需要重新建立本地服务端的项目；也适用于已经找到部分网络函数或 Opcode，但尚未打通登录、进入地图或持续交互的工程。

它约束 Agent 不只交付一份路线介绍，而是在具备工具和运行条件时，直接进行分析、实现、实验与回归，并持续保存能够被下一轮工作接手的记录。

**目标是兼容性重建，不是宣称找回官方内部实现。** 协议兼容、客户端可见行为兼容与官方服务端逻辑一致，是三个不同层次。缺少依据的战斗公式、AI、掉落和经济参数，应作为可替换的“重建规则”明确记录。

默认不建设跨服、分布式、商业运营或大规模并发架构，也不以导出全部美术资源、找到全部 Opcode 为开始实现的前提。

## 技术栈约定

| 部分 | 约定 |
| --- | --- |
| 服务端 | **Go 或 Python 二选一**，先快速构建最小可运行原型，不同时维护两套实现 |
| 数据库 | **SQLite**，负责账号、角色、位置、背包等存档；按需迁移表结构 |
| 服务结构 | 优先单进程、少依赖；不默认引入分布式组件和独立数据库服务 |
| 诊断记录 | 原始事件使用 JSONL，自动导出 JSON / CSV / Markdown；需要数据库索引时仍使用 SQLite |
| 资源速查 | 可选的本地只读网页，围绕资源、Lua、Opcode 和异常记录建立关联 |

已有 Go/Python 工程优先沿用；新工程没有偏好时先用 Python，指定 Go 时使用 Go。SQLite 从原型阶段接入，不等玩法全部实现后才补存档。建议游戏数据放在 `data/game.db`；大量诊断记录与角色存档分离，诊断索引可放在另一个 SQLite 文件中。

接手其他语言或数据库的旧工程时，保留基线与数据备份，再制定最小迁移路径；不要破坏性重写，也不要把“旧工程暂时能运行”写成已经符合当前技术栈约定。

## 快速开始

### 1. 准备客户端与工作目录

保留一份只读原始客户端，为实验创建工作副本。向 Agent 提供实际路径，并尽可能提供客户端版本、启动入口、当前报错、已有分析和允许修改的范围。

以下仅为路径示例，请替换为自己的实际目录：

```text
D:/GameRevival/
├── client-original/    # 原始客户端，只读保留
├── client-working/     # 工作副本，用于本地联调
└── workspace/          # 分析、协议、服务端与测试工程
```

原始材料可以只记录路径和 SHA-256，不必为满足目录结构重复复制大型证据。已有服务端工程和分析目录应优先沿用。

### 2. 让 Agent 读取 Skill

使用支持 Skill 的 Agent 时，按该工具自身的加载规则放置 `offline-mmo-revival` 目录，并确认 `SKILL.md` 已被读取。本文不预设某个产品的专用安装路径。

没有 Skill 加载机制时，可以让能访问本地文件的 Agent 直接读取 `SKILL.md`；也可以将文件作为附件提供，或把其中的指令放入任务上下文。

> 加载 Skill 不会自动提供调试器、文件访问、命令执行或客户端运行能力。应按实际环境提供工具；只能做静态分析时，必须明确哪些结果尚未经过真实客户端验证。

## 执行阶段与验收

阶段编号用于管理进度，不要求严格单向执行。可以从脚本、网络函数或 Dispatcher 入手，再沿当前目标的依赖补齐。

| 阶段 | 主要工作 | 阶段验收重点 |
| --- | --- | --- |
| 0 · 运行基线 | 核实启动链、依赖、配置与初始连接行为 | 能重复到达同一状态，或有证据说明运行阻塞 |
| 1 · 客户端结构 | 定位关键模块、调用链、消息构造与读取入口 | 有可追溯的函数候选与下一步验证目标 |
| 2 · 必要资源与脚本 | 只提取登录/进图必需内容，不先做全量解包 | 来源明确，提取过程可复现 |
| 3 · 网络与变换边界 | 关联线上字节、变换前后缓冲区和业务读写 | 能解释数据处于哪一处理层 |
| 4 · Packet 格式 | 确认分帧、字段、会话变换与状态更新规则 | 当前消息有独立证据和边界测试支持 |
| 5 · Dispatcher / Opcode | 建立消息、处理入口、字段与前置状态映射 | 关键消息可解释、可定位、可复现 |
| 6 · 最小服务端 | Go/Python + SQLite，建立传输、派发、状态机与诊断入口 | 完成至少一个真实客户端协议交互 |
| 7 · Login | 实现实际存在的协商、认证和角色选择依赖 | 从干净启动稳定进入角色选择或等价阶段 |
| 8 · EnterWorld | 补齐角色、地图、实体与初始化顺序 | 能进入地图并操作，移动与心跳正常 |
| 8A · 进游戏后资源分析 | 系统解包、提取 Lua、整理 Opcode；可选速查网页 | 有资源来源、脚本/消息索引、覆盖范围与缺失项 |
| 9 · 诊断与逻辑还原 | 附加记录、自动导出、用户回填、Lua 定位、修复与 Oracle 验证 | 问题可追溯，修复经过真实客户端复测 |
| 10 · 玩法与存档 | 建立最小玩法循环、权威状态及 SQLite 存档 | 保存、服务端重启、重登和重复操作可验证 |

## 进入游戏后：资源、Lua 与 Opcode 索引

首次进入地图并能操作后，先保存成功基线，再系统解包客户端资源。优先整理 Lua、消息配置、地图、NPC、物品、技能和任务数据；美术资源按实际需求扩展，不要求一次导出全部内容。

Lua 提取需要区分源码、字节码和定制变体，保留原件、导出方法和分析产物。静态提取不足时，可以在授权本地进程的实际加载边界补充记录已加载模块，但不能把这一轮加载过的脚本当成全部脚本。没有 Lua 的客户端使用实际脚本系统或原生处理器，缺失内容单独列出。

**Opcode 列表不是只列“编号 + 名称”。** 应联合 Lua 常量、消息注册、发送封装、接收回调、原生 Dispatcher 和运行记录，形成以下关系：

```text
用户操作 / 功能
    ↕
Lua 文件、函数、字段读写与前置条件
    ↕
连接 + 方向 + 协议阶段 + Opcode / 子码
    ↕
客户端处理器 ↔ Go/Python Handler ↔ 游戏状态 / SQLite 存档
    ↕
关联资源 ↔ 用户测试 ↔ 异常记录 ↔ 复测证据
```

消息目录导出为 `protocol/opcodes.json` 和 `protocol/opcodes.csv`，保留来源及覆盖范围。网络 Opcode、脚本事件编号和 Lua 字节码指令编号必须区分；没有证据的数字不能直接放进“已确认协议”列表。

### 可选：资源速查网页

在已有资源或脚本索引的基础上建立本地只读页面，支持按名称、ID、类型、路径、Lua 函数、Opcode 或实现状态查询。详情页展示资源来源、脚本片段、处理器和关联问题；已有转换条件的图片等资源可以增加预览。

页面用于回答“这个物品 ID 是什么”“这个按钮调用哪段 Lua”“这个 Opcode 还有什么没实现”，不需要先做完整管理平台。默认仅本地访问，不执行浏览到的脚本、不上传资源；尚未实现网页时照常推进协议与玩法修复。

## 附加诊断与异常 Opcode 自动导出

**服务端结构化日志是基础，Attach 附加诊断是可用时补充的观察手段。** 根据当前工具和客户端条件，可以附加到正在运行的本地客户端或自建服务端，记录消息、处理器、Lua 错误与用户行为；不能附加时保留服务端日志和人工测试回填路径。

观测应优先放在已经确认的明文/编解码、Dispatcher、Handler 和 Lua 绑定边界，不修改返回值来制造成功。每轮用 `run_id` 区分测试，每个用户操作用本地 `action_id` 标记，关联前置条件、相关消息、预期与实际现象。附加位置、采集缺口、截断和丢事件要一起记录。

自动记录的重点包括未知 Opcode、未实现/Stub、解析或状态错误、Handler 异常、有依据的响应超时、Lua 错误、缺失资源和客户端行为不符。**没有回包不一定是失败，Handler 返回成功也不等于功能正常。** 功能没反应但未观察到发包时，保留操作级问题，不随便把它归因于最后一个 Opcode。

### 自动产物

下列文件由使用 Skill 的实际工程实现并生成，当前仓库不附带采集器或示例运行结果。

| 文件 | 作用 |
| --- | --- |
| `logs/<run_id>/opcode-events.jsonl` | 逐事件追加原始诊断及上下文、样本引用 |
| `reports/<run_id>/opcode-summary.json` | 供 Agent 读取的消息覆盖、问题、证据与反馈关联 |
| `reports/<run_id>/opcode-summary.csv` | 供用户筛选的 Opcode、功能、实现状态、异常和测试结果 |
| `reports/<run_id>/opcode-issues.md` | 按功能与依赖整理的待修复问题、复现步骤和 Lua 线索 |
| `reports/<run_id>/user-test-checklist.csv` | 用户测试清单，包含步骤、预期、实际、结果和关联消息 |
| `reports/<run_id>/user-feedback.csv` | 独立保存的用户回填副本，避免被自动刷新覆盖 |

事件增量写入，汇总按配置定期刷新；一轮测试结束、正常断开或退出时自动导出，也应提供手动导出入口。崩溃后的汇总只能从已经落盘的数据恢复，需标注中断与缺失范围，不宣称零丢失。

汇总不能只按 Opcode 数字去重，要考虑客户端版本、连接、方向、协议阶段和故障特征。保留稳定 `issue_id`，将自动观察、用户反馈与修复状态分别维护；从未被测试的功能不自动标记为正常。

### 用户测试后如何推进

```text
启动 Go/Python 服务端与客户端，开启诊断
→ 用户选择一个可达功能，标记测试开始与结束
→ 正常操作，填写预期结果、实际现象和复现步骤
→ 自动导出报告，保存独立的用户回填文件
→ Agent 读取报告并归并问题，梳理 Opcode 与消息依赖
→ 查找本地 Lua 发送封装、接收回调、字段与资源引用
→ 结合原生代码与运行证据重建逻辑，修复服务端和 SQLite 状态
→ 同条件复测；涉及存档的功能继续验证重启重登
→ 更新问题状态、Opcode 表、证据与 PROGRESS.md
```

用户测试结果使用 `not_tested / pass / fail / blocked`，与 `todo / stub / partial / complete` 这样的实现状态独立。修复后先标为 `fixed_pending_retest`，通过指定客户端和操作的复测后才标为 `verified_closed`；无法复现不等于已经修好。

Lua 中的字段读写、回调、前置条件和错误分支是重要分析依据，但展示或预测逻辑不能直接充当服务端权威规则。缺失的官方逻辑仍应标为可替换的重建规则。

```text
没有执行客户端复测的项目保持 fixed_pending_retest，不宣称已完成。
```

## 怎样使用客户端作为协议 Oracle

这里的 **Oracle** 指实验中的观察与验证依据：针对同一客户端版本、同一前置状态，构造有证据支持的候选响应，观察客户端如何解析、迁移状态并发出后续消息。

```text
选择一个可观察目标
→ 固定客户端版本、会话与角色初始状态
→ 提出一个字段、消息或时序假设
→ 构造最小候选响应
→ 只改变一个语义变量及其必需的派生字段
→ 比较解析、状态、业务结果与反例
→ 保存证据，更新规格、实现与回归测试
```

例如，登录成功后仍停留在加载界面，不应直接得出“还缺一个进入世界 Opcode”的结论。应结合客户端接收路径，检查当前初始化依赖是否满足，再验证角色信息、地图资源、对象引用、连接切换或完成标记等候选原因。

**没崩溃、没断线、出现模型，都不能单独作为功能完成的依据。** 需要进一步确认完整读取、正确状态迁移、预期业务变化，以及后续交互和必要的重登结果。

客户端接受某个响应，也不代表响应中的玩法算法或数值与原官方服务端一致。

## 推荐工作区与产出

以下是实际重建项目可按需采用的结构，不要求迁移已有工程：

```text
workspace/
├── PROGRESS.md       # 当前阶段、成功闭环、阻塞与下一项实验
├── evidence/         # 样本清单、哈希、抓包、追踪和截图
├── extracted/        # 提取资源、lua/、原件与分析产物的来源关系
├── analysis/         # 函数定位、调用关系和实验记录
├── protocol/         # Packet 规格、opcodes.json/csv 与逐消息定义
├── server/           # Go 或 Python 独立服务端
├── data/             # SQLite 游戏存档与独立诊断/资源索引
├── instrumentation/  # 按客户端版本编写的附加诊断配置/脚本
├── logs/             # 按 run_id 记录原始事件 JSONL
├── reports/          # 自动导出、用户回填与复测记录
├── tools/            # 解包、Lua/Opcode 索引与导出工具
├── resource-browser/ # 可选：本地资源速查网页
└── tests/            # 编解码、状态机、回放和客户端回归测试
```

每条 Opcode 记录需要关联版本、连接类型、方向、协议阶段、处理入口、字段、前置状态和证据。**证据状态、实现状态和验证范围应分别维护**，不能因为写出了 Handler，就将推测升级为已确认协议。

| 维度 | 记录方式 | 含义 |
| --- | --- | --- |
| 证据状态 | `unknown` / `inferred` / `verified` | 尚未确定、推测、有明确范围的验证支持 |
| 实现状态 | `todo` / `stub` / `partial` / `complete` | 未实现、临时占位、部分实现、实现完成 |
| 验证范围 | `static` / `codec` / `server` / `client` / `cold-start` | 静态、编解码、服务端、客户端联调、冷启动回归 |

`verified` 必须附带适用条件；`complete` 也不自动代表已完成客户端联调。完整 Opcode 模板与实验记录要求见 [SKILL.md](./SKILL.md)。

每轮工作采用以下报告格式，便于定位进度并继续执行：

```text
当前目标：本轮要解锁什么客户端行为。
已确认：结论、适用版本/状态及证据位置。
本轮变更：新增或修改了哪些文件、消息定义和实现。
验证结果：实际执行的测试，以及通过、失败、未运行的部分。
测试与导出：本轮 run_id、报告路径、用户回填结果和新增/待复测/关闭问题。
当前阻塞：缺少的事实、失败层次与尚未排除的假设。
下一步：一个最值得执行的实验及其判定条件。
```

## 完成标准

项目至少需要完成一次可重复的“启动、登录、进地图、基础交互、最小玩法循环、保存、重启服务端、重登恢复”闭环，并交付能够复现该结果的 Go/Python 服务端源码、启动说明、SQLite 初始化/迁移/恢复方式、连接配置、协议记录、测试及已知问题。

还应交付资源解包与 Lua/Opcode 索引流程、已实现的诊断及自动导出工具、用户测试回填与复测说明。附加不可用时列明替代方式和采集缺口；资源速查网页可选，做了再提供实际启动方式。没有实现的工具必须列为未完成，不能把本文的功能要求当成已经交付的软件。

最终报告必须分别标注：**原版客户端已验证兼容、仅修改连接配置后兼容、代码修改版才兼容、已实现但未联调、临时 Stub、自行设计的重建玩法，以及尚缺证据的功能。**

成功标准是一个版本明确、行为可验证、存档可持续的新服务端，而不是一张看起来完整的 Opcode 表。

## 常见问题

### 没有官方服务端和历史抓包，还能开始吗？

可以从客户端的消息构造、读取逻辑、脚本注册和状态切换入手，先建立候选消息规格，再用本地服务端逐步验证。没有参考回包时，更需要严格区分推测与验证结果，不能凭空补齐未知协议。

### 必须先解出所有资源、所有脚本和全部 Opcode 吗？

不需要先完成全量提取。登录/进图前只处理必需内容；首次能够进入地图并操作后，应系统解包并整理 Lua 与 Opcode 索引。某项提取方法是否适用由实际加载流程验证，不预设所有客户端都有 Lua、都有静态 Opcode 表或能恢复完整源码。

### 服务端语言和数据库如何选择？

本版要求服务端使用 **Go 或 Python 二选一**，数据库使用 **SQLite**。已有 Go/Python 工程沿用，空白项目默认 Python；不要求同时写两套服务端，也不把 MySQL 等独立数据库作为默认依赖。

### 附加记录可以自动判断所有功能是否正确吗？

不能把采集结果当成完整判定。应结合用户操作、消息依赖、Handler/Lua 行为和客户端实际效果，保留待确认与未测试项。附加本身不可用时，继续使用服务端日志和人工回填，并明确客户端侧观测缺口。

### 资源速查网页是必须的吗？

不是。资源解包、Lua/Opcode 索引属于进游戏后的工作，网页是在索引可用且条件允许时增加的辅助工具，不能阻塞核心功能修复。

### 能保证原客户端完全不改就能使用吗？

不保证。项目需要如实记录原始版本、连接配置变更和代码变更，分别说明兼容范围。遇到无法取得的原服务端签名或信任材料时，应将其列为明确阻塞；采用本地信任替换的实验版本，不得宣称原版无修改兼容。

### Agent 不能运行游戏时怎么办？

继续完成可执行的静态分析、协议规格、服务端代码和离线测试，并给出针对缺失证据的采集步骤。未运行的客户端联调必须标记为未验证，不能用自行编写的编码器与解码器互测代替原客户端验证。
